**Root cause (WHY it stranded):** the old model kept ONE `telegram_message_id` per merchant group with "adopt an existing id, don't resend." A prompt covers only ONE dimension, and group members can be in heterogeneous states. So once a group was partially resolved (payee settled, category open — or vice-versa) or a new transaction joined a group that already had an (answered) prompt, the still-open dimension was never re-prompted. Those transactions sat in `pending_reviews` forever — never imported, invisible in Actual. Diagnosed from a live `state.toml`: every stuck entry had exactly one dimension settled + a lingering `telegram_message_id` (e.g. `MR FERNANDO MACEDO FERREIRA` = 7 entries sharing msg 135, mixed payee states).

**The fix (architecture now on main):**
- New field `PendingReview.prompted_dimension: Option<PromptDimension>` (`Payee`/`Category`, serde `rename_all="lowercase"`, `#[serde(default)]` → NO state version bump; absent = `None`). Plus `PendingReview::open_dimension()` (payee-first, then category, then none).
- Single enforcer `telegram::prompts::ensure_prompts(state, channel, payee_names, category_names, state_path)` called by BOTH `run` (after import) and `poll` (after applying replies, using the cached `actual_*_names` catalogs). Per-group invariant: the group's open question is payee-first; re-prompt iff no member holds a live prompt whose `prompted_dimension` == that question. Stamps `(id, dimension)` on ALL members; best-effort `edit_message_text` tidies a superseded prompt; warn-and-continue on send/edit/persist failure (no-spam preserved: unanswered same-dimension prompt is not resent).
- **REMOVED** (do NOT reference — deleted): `send_group_prompts`, `send_group_prompts_inner`, `send_chained_category_prompts`, and poll's `chain_after_payee_settle`. This SUPERSEDES the Phase D poll-side chaining in [[review-remediation-phases]].
- Payee mutators `create_pending`/`remap_pending`/`confirm_pending` now no-op on an already-`payee_settled()` member (a group-wide reply can't corrupt a settled sibling).
- **Auto-heal (free):** existing stranded entries load with `prompted_dimension = None` → mismatch → each gets exactly one correct prompt on the first run/poll after deploy; the ~45-entry backlog surfaces itself (no manual state editing).
- Spec/plan: `docs/superpowers/{specs,plans}/2026-07-24-stranded-pending-reviews*.md`. Subagent-driven (6 tasks, per-task + whole-branch opus review). Gate at merge: 182 tests, clippy `-D warnings`, fmt all clean.

**FOLLOW-ON FIX shipped `41a4264` (pushed 2026-07-24, NOT yet redeployed):** the terminal prompt keyboard was never cleared. `ensure_prompts` tore down a group's inline keyboard ONLY on the chaining path (payee settled → send category prompt does a best-effort `edit_message_text` on the old id). When a tap FULLY resolved a group (`group_question` → `None`), the code just `continue`d → the final button dangled in Telegram forever. In a multi-reply poll batch only the groups that *chained* got cleared → user saw "only 1 of my taps registered" (the item WAS added; idempotent re-taps are correct/no-ops — the only defect was the stale message). **WHY non-obvious:** keyboard teardown was coupled to *re-prompting*, not to *resolution*; the terminal state has no next prompt to send, so it silently skipped cleanup. **Fix:** the `None` branch now edits the message once (`✅ <payee> → <category>` via new `resolved_summary()` helper) and nulls `telegram_message_id`/`prompted_dimension`. **Only `poll` can clear** — `run`'s `ensure_prompts` runs AFTER `take_resolved()` has already removed the resolved review, so run never sees it; poll applies the reply and calls `ensure_prompts` in the same tick while the review is still pending. Verified with 3 tests incl. a poll-integration one proving the batch reply-loop itself never drops replies (so the "multiple taps don't stick" feeling was purely the missing feedback). Pre-existing already-imported groups keep an inert orphaned button (no state references them) — not worth special-casing.

**LATENT (noticed, NOT fixed, hasn't bitten):** `parse_get_updates` sets `new_offset = max_update_id + 1` over EVERY fetched update, and `poll` skips replies whose `entry_key` isn't in `valid` (or a category `PickCategory` hash that doesn't resolve against `state.actual_category_names`) — so a reply that fails to correlate at that tick is acked and lost forever (e.g. a free-text reply to a SUPERSEDED message id, or a pick when the category snapshot is stale/empty). Correct-for-foreign-spam, wrong-for-our-own-uncorrelated-replies. Revisit if reply-loss recurs after the keyboard fix deploys.
