# Pre-Deploy Security & Correctness Audit — `aba` (Actual Budget Automation)

> Multi-agent audit, 2026-06-02. 8 area finders across all dimensions → adversarial
> verification (skeptic per finding) → Opus synthesis. 51 findings raised, **50 confirmed,
> 1 refuted**; deduped to ~22 distinct root issues. Method/script:
> `aba-deep-audit` workflow.

**Audit scope:** Full pre-first-production audit of a one-shot nightly Rust CLI that moves real financial data (Monzo → payee matching → Actual Budget import) with a Telegram confirm/correct side-channel.
**Repo:** `G:/rustDev/actual-budget-automation` · **Branch:** `main` · **Runtime target:** headless Linux Docker container, non-root `node` uid 1000.

---

## 1. Executive Summary

**Overall risk posture: NOT READY FOR FIRST DEPLOY.** The codebase is, on the whole, thoughtfully built — the hard invariants are mostly respected, the atomic-save and lock discipline is sound, and the secret-redaction pattern exists where it matters most. But there is **one critical data-loss bug** and **three high-severity availability/correctness bugs** that directly threaten the project's stated core invariants (fail-loud fetch, `last_run` gating, no silent loss). For a tool that moves real money on an unattended nightly schedule with no external watchdog, these must be fixed before the first push.

**Recommendation: NO-GO until the 1 critical + 4 high blockers below are fixed and regression-tested.** The fixes are small and localized (roughly a day of work). Once they land, the medium/low items can be addressed in a fast follow before or shortly after deploy. The good news: there are no architectural defects — every blocker is a missing guard, not a design flaw.

**Severity tally (deduped):** 1 critical · 4 high · 6 medium · 8 low · 3 info.

## 2. Deploy Blockers (must fix before push)

### BLOCKER 1 — [CRITICAL] Hallucinated payee name silently drops a transaction → permanent data loss
- **File:** `src/run.rs:324-326` (drop), `src/run.rs:431` (`last_run` advances)
- **Dimension:** correctness
- **Impact:** When Claude returns a high-confidence payee name that does **not** exactly match an existing Actual payee (`payee_id_for` returns `None`), the `(Some(_), None)` arm only logs `warn!` and falls through. The transaction is **not** imported, **not** held for review, and **not** cached — yet `state.last_run = Some(Utc::now())` advances unconditionally at line 431. `fetch_since(last_run)` will never re-fetch it. **The transaction is permanently lost from the budget.** This is the single most serious issue in the audit: it is a direct violation of the FAIL-LOUD invariant (a partially-successful run still advances `last_run`), it fires on routine Claude name variance (e.g. Claude returns "Transport for London" while Actual has "TfL Travel"), and it is silent — the only trace is one `warn!` line. Confirmed by reading the code directly.
- **Fix:** In the `(Some(_), None)` arm, route the transaction to Telegram review via `state.add_pending_full(...)` with the proposed name as the suggestion, instead of dropping it. Alternatively, validate every Claude-returned payee name against the live payee list inside `apply_matches` before it reaches auto-import, demoting any non-existent name to `unmatched`. Either way: **never advance `last_run` if any matched transaction was silently skipped.** Add a regression test for the high-confidence-match-with-no-existing-payee path.

### BLOCKER 2 — [HIGH] No timeout anywhere → unattended container hangs forever
- **Files:** `src/banks/monzo.rs:63`, `src/claude.rs:153`, `src/telegram.rs:180`, `src/notify.rs:21`, `src/run.rs:537` (all `reqwest::Client::new()`), **and** `src/actual/mod.rs:70` (`child.wait_with_output()`)
- **Dimension:** correctness
- **Impact:** No reqwest client has a connect/read/total timeout, and the Node shim wait has no `tokio::time::timeout`. Any stalled TCP connection or hung shim blocks the process indefinitely. There is no external watchdog. A hung `run` holds the advisory lock and the container never exits, so every subsequent nightly cron invocation also stalls/piles up. (Merges three duplicate findings covering the same root cause across HTTP clients and the shim wait.)
- **Fix:** Build every client with `reqwest::Client::builder().connect_timeout(Duration::from_secs(10)).timeout(Duration::from_secs(30)).build()?`. Wrap `child.wait_with_output()` in `tokio::time::timeout(Duration::from_secs(120), ...)` and `child.kill().await.ok()` on timeout. Add a top-level `tokio::time::timeout` around the whole `run()`/`poll()` as a backstop.

### BLOCKER 3 — [HIGH] Unescaped Markdown in Telegram prompt → transaction permanently stuck in held state
- **File:** `src/run.rs:143-165` (interpolation), `src/telegram.rs:157` (`"parse_mode": "Markdown"`)
- **Dimension:** correctness
- **Impact:** Bank-controlled `raw_merchant` (and Claude suggestion `s`) are interpolated verbatim into Markdown v1. A merchant name with unbalanced backticks/asterisks/underscores (e.g. `` HALF`PRICE ``) makes Telegram return HTTP 400 "can't parse entities". `send_prompt` errors → caught by `warn!` → `telegram_message_id` stays `None` → re-sent every run → fails identically forever. Meanwhile `last_run` already advanced (line 431), so the transaction is never re-fetched. **Net effect: a held transaction is invisible to the user permanently and never imported.**
- **Fix:** Simplest and safest — drop `parse_mode` entirely and send plain text with ASCII delimiters (eliminates the injection surface). Otherwise switch to MarkdownV2 with a full special-character escaper. Add a test with a merchant name containing backticks and asterisks.

### BLOCKER 4 — [HIGH] `ACTUAL_PASSWORD` exposure via inherited shim stderr
- **File:** `src/actual/mod.rs:56-58`
- **Dimension:** security
- **Impact:** The shim is spawned with `.stderr(Stdio::inherit())` while `ACTUAL_PASSWORD` is passed as an env var. The shim's own code is clean (errors go to stdout as JSON), but `@actual-app/api` is a third-party library that may emit auth diagnostics to stderr — those would flow verbatim into the container log stream (journald/json-file). This is the widest unredacted secret surface in the pipeline. (Severity is borderline high/medium — the confirmed leak path is conditional on library behaviour, but for a financial tool's first deploy it warrants blocker treatment alongside the cheap fix.)
- **Fix:** Capture stderr with `Stdio::piped()` via the existing `wait_with_output()` call, redact the password substring, and emit only on non-zero exit via `tracing::debug!`/`error!`.

> **If you fix nothing else before deploy, fix these four.** Blocker 1 loses money silently; Blockers 2 and 3 brick the nightly job; Blocker 4 risks leaking the budget password into logs.

## 4. Cross-Cutting Themes

1. **No timeouts anywhere (availability).** Every outbound boundary — 5 reqwest clients, the shim wait, the OAuth listener — is unbounded. For an unattended one-shot cron job with no watchdog, this is the single biggest reliability pattern and the root of two high findings. A blanket timeout policy fixes the class.

2. **`last_run` advances on too many partial-failure paths (the FAIL-LOUD theme).** Three distinct findings (C1 silent drop, H2 stuck-prompt, M1 wall-clock cursor) all reduce to the same root: `state.last_run = Some(Utc::now())` at `run.rs:431` runs unconditionally even when individual transactions were silently skipped or arrived mid-window. The invariant's *intent* — advance only when truly everything was captured — is not enforced per-transaction. Consider gating `last_run` advancement on "zero silently-skipped transactions" and using a fetch-start cursor.

3. **Redaction applied inconsistently (secrets).** The `redact()` helper exists and is used correctly on Telegram transport/JSON-parse errors and is the right pattern — but it's skipped on the three HTTP-status-error arms (M2), absent for the shim password path (L6, H3), and the `Debug` derives on `Config`/`State`/`MonzoState` are latent leaks (L4, L5). The team clearly knows the pattern; the gap is uniform application. A `Secret<T>` newtype would close most of these structurally.

4. **Silent `filter_map`/fall-through drops.** Both `schedules_from_rows` drops (M4, M5) and the hallucinated-payee drop (C1) share an anti-pattern: discarding data inside a closure or match arm with at most a `warn!`. For a financial tool, "drop + log" should be "drop loudly + ensure recoverable."

5. **Third-party library trust (`@actual-app/api`).** Several findings (H3/L6 password echo, L2 exit status, shim stdout contamination) hinge on behaviour of a heavyweight library that writes to the real budget DB. Defensive piping/redaction around the shim boundary would neutralize this whole class.

## 5. What Looked Solid (verified)

These are genuine strengths and raise confidence that the design is sound once the guards are added:

- **`last_run` gating on the happy/error path is correct.** `state.last_run = Some(Utc::now())` at `run.rs:431` is reached *only after* `import_transactions` succeeds (the `?` at line 424 returns early on failure), and `state.save()` at line 452 is only reached on success. On import failure, the pending review survives on disk for clean retry. Invariant 2 holds in current code (the gap is missing *test* coverage, not a bug).
- **Dry-run discipline.** Dry-run short-circuits before `last_run` advancement and before persisting reviews/cache; only a rotated refresh token may be persisted. Verified across the dry-run tests.
- **Atomic state writes.** `State::save` uses write-to-`.tmp`-then-`rename`, which is atomic on a single filesystem — the correct pattern. The only gap is the cross-FS EXDEV edge (M8), which fails *loudly* and preserves the invariant.
- **Concurrency model.** `poll` is the sole Telegram reader/offset-owner and never writes Actual; `run` is the sole Actual writer; they serialize on the advisory `<state>.lock`. The Telegram crash-replay window is provably idempotent for all four reply types.
- **OAuth state nonce** is generated and verified correctly, and the callback listener binds `127.0.0.1` only (no remote exposure).
- **Redaction core.** `redact()` correctly strips the bot token from transport and JSON-parse errors — the most common error paths — and the URL-building is the only place the token appears.
- **The shim's own code is clean.** `actual-shim/index.js` writes only JSON to stdout, wraps everything in try/catch, and never `console.error`s — the credential risks are all in the third-party library boundary, not the shim itself.
- **`create_payee` orphan self-heals.** Contrary to the "N duplicate payees" claim in several findings, `get_payees()` is re-fetched each run and `payee_id_for` finds the prior orphan by name, so at most one transient orphan is created and reused on retry (L1).
- **Build/dep reproducibility basics.** `Cargo.lock` and `package-lock.json` are committed and `npm ci`/locked `cargo build` are used in the Dockerfile — reproducibility is mostly in place; the gaps are digest pinning and audit gating, not lock discipline.
